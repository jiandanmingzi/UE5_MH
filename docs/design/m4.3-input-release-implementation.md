# M4.3：OnReleaseIfUnconsumed 输入释放补丁——设计与实施

> **阶段：M4.3（C++ / 运行时，已签收于 2026-08-29）。** 本文是 `OnReleaseIfUnconsumed` 的唯一实施合同。Development Editor 编译通过；`MHGZ.M4.3.Input` 7/7 与 `MHGZ.M1.Input` 9/9 通过。阶段顺序、当前状态与完成裁定以 [阶段门禁](milestone-gates.md) 为准；虫棍招式和最终 InputProfile 资产接线仍分别以 [动作设计](insect-glaive-actions.md) 与 [编辑器接线指南](../editor/demo-setup.md) 为准。

> **目标：** 让持刀地面单 RT 成为“按住期间可参与 LT/A/B/Y 组合；本次按压未被任何获胜组合消费时，松开 RT 才输出一次 `Input.Weapon.RT`”的通用 Router 能力。它为后续 `GA_IG_MarkSlash` 预备输入语义，**本阶段不创建、授予或激活该 GA**。

## 1. 完成边界

M4.3 只修改输入声明、输入 Router 和自动化测试。完成后，`UWeaponInputProfile` 能声明 `OnPress` 或 `OnReleaseIfUnconsumed`；Router 能正确输出不可变 `Started` 快照；既有组合、释放身份和所有 `OnPress` Chord 保持原行为。

不在本阶段做下列事项：

1. 不修改 `UGA_WeaponComboCoordinator`、`UMHGZAbilitySystemComponent`、`UMHGZWeaponRuntimeHostComponent` 或任意具体 GA。
2. 不创建虫印斩、AttackSegment、Combo Transition、Montage、Exit PSD/Chooser 或动作退出逻辑。
3. 不在 `DA_IG_InputProfile` 中提前把正式持刀 RT 改成新策略；该资产回填属于 **E4.3**，并在 M4.7 有 `GA_IG_MarkSlash` 后才具有玩法消费者。
4. 不把“松开”转成新的 `Completed` 语义；原有 `Completed` 仍只给已注册的激活身份。

## 2. 已核对的现有链路

~~~text
Enhanced Input Started / Completed
  -> UMHGZInputComponent
  -> UMHGZWeaponInputRouterComponent
       HeldControls[PhysicalTag] { StartedTime, SequenceID, ... }
       Chord 排序 / DeferredChords / bSingleConsumed
       EmitSnapshot(FWeaponInputSnapshot)
  -> UMHGZAbilitySystemComponent
       Input.Weapon.* -> UGA_WeaponComboCoordinator
       其他 InputTag -> 直接按 InputTag 激活 Core Ability
  -> UMHGZWeaponRuntimeHostComponent
       Completed 仅按 SourceControlTag + SequenceID 分发给当前 Active Action
~~~

现有实现中，`FPhysicalInputState::SequenceID` 在每次物理 `Started` 时分配；`FWeaponInputSnapshot` 由 Router 冻结；`ReleaseRegistry` 只登记已经在按下/组合解析时发出的动作，用于之后发送同身份的 `Completed`。这些合同不应被 M4.3 改写。

当前文件职责如下：

| 文件 | M4.3 前已有职责 | M4.3 变更 |
|---|---|---|
| `WeaponRuntime/MHGZWeaponInputProfile.h` | `FWeaponChordDefinition` 的反射字段 | 新增派发策略枚举和字段。 |

| `InputSystem/MHGZWeaponInputRouterComponent.h/.cpp` | Chord 解析、快照、释放身份 | 将 release-fallback 与 OnPress Chord 分开解析，并记录本次物理按压是否被获胜组合消费。 |

`UMHGZAbilitySystemComponent::HandleResolvedInputSnapshot`、`HandleResolvedInputRelease` 和 `UMHGZWeaponRuntimeHostComponent::DispatchInputRelease` 已经能处理新快照，不应在本阶段增加分支。

## 3. 数据模型与合法配置

### 3.1 新枚举与字段

在 `MHGZWeaponInputProfile.h`、`FWeaponChordDefinition` 前定义：

```cpp
UENUM(BlueprintType)
enum class EWeaponChordDispatchPolicy : uint8
{
    OnPress UMETA(DisplayName = "On Press"),
    OnReleaseIfUnconsumed UMETA(DisplayName = "On Release If Unconsumed")
};
```

在 `FWeaponChordDefinition` 的 `Chord` 分类新增：

```cpp
UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Chord")
EWeaponChordDispatchPolicy DispatchPolicy = EWeaponChordDispatchPolicy::OnPress;
```

默认值必须为 `OnPress`，以保证所有现有 DataAsset 和所有未修改 Chord 的序列化、派发时机和释放逻辑不变。

### 3.2 `OnReleaseIfUnconsumed` 的严格声明规则

该策略是一个按物理键归属的兜底，不是普通 Chord。因此 Data Validation 必须拒绝：

| 规则 | 原因 |
|---|---|
| `TriggerControls.Num() != 1` | 无法定义唯一的物理按压与 `SequenceID`。 |
| `RequiredHeldModifiers` 非空 | 组合应仍由普通 `OnPress` Chord 在形成时胜出并消费兜底。 |
| `ReleaseControlTag` 有效 | 此策略在同一次松开时才产生 `Started`，绝不能再登记同键 `Completed`。 |
| 同一物理 Trigger 存在两条 release-fallback Chord | 松开时会出现两个潜在输出，不能依靠 Priority 隐式裁决。 |

`OutputTag`、物理 Tag 映射、ContextTags 合法性、Trigger/Modifier 重叠、`bRequireExactModifiers` 的原有校验继续执行。`bConsumeTriggerControls` 对 release-fallback 没有独立效果：它不会在按下时胜出，也不会产生下一次物理按压前可消费的单键输出；保留字段值以避免为此策略创建额外特例。

### 3.3 最终虫棍配置（延后至 E4.3）

正式资产回填时，持刀地面 RT 的唯一 release-fallback Chord 固定为：

| 字段 | 值 |
|---|---|
| `OutputTag` | `Input.Weapon.RT` |
| `TriggerControls` | `[Input.Modifier.RT]` |
| `RequiredHeldModifiers` | `[]` |
| `RequiredContextTags` | `Combat.State.Unsheathed`、`Combat.State.Grounded` |
| `bRequireExactModifiers` | `true` |
| `DispatchPolicy` | `OnReleaseIfUnconsumed` |
| `ReleaseControlTag` | `None` |
| `AimSnapshotContext` | `None` |

收刀地面 RT 与空中 RT 仍使用 `OnPress`，并以互斥 ContextTags 与持刀地面 RT 分流。持刀 RT 与 LT/A/B/Y 形成的正式组合继续是普通 `OnPress` Chord；任何一个获胜组合都消费本次 RT 的 release-fallback。

## 4. 运行时状态与不变量

### 4.1 新增私有状态

在 `UMHGZWeaponInputRouterComponent` 中新增以下**私有**状态；不暴露 Blueprint API：

```cpp
// FPhysicalInputState 内
bool bReleaseFallbackConsumed = false;

// Router 内，RebuildChordCache 生成
TMap<FGameplayTag, int32> ReleaseFallbackChordByControl;
TSet<FGameplayTag> ReleaseFallbackOwnedTags;
```

- `bReleaseFallbackConsumed` 属于一次物理按压；下一次 `Started` 必定重置为 `false`。
- `ReleaseFallbackChordByControl` 保证每个物理键最多找到一条合法的策略 Chord。
- `ReleaseFallbackOwnedTags` 防止只有 release-fallback 的物理键在按下、Grace 到期或快速松开时退化为原始 PhysicalTag 单键输出。
- 不新增 ReleaseRegistry 条目；release-fallback 的 `Started` 就在这一次 `Completed` 处理内发出，之后已经没有下一次可匹配的物理 `Completed`。

### 4.2 消费不变量

一次物理 RT 按压满足下列其中之一：

| 结果 | `bReleaseFallbackConsumed` | 松开 RT 时输出 |
|---|---:|---|
| 某个普通 Chord 获胜，且 RT 是其 Trigger 或 Modifier | `true` | 仅保留该既有 Chord 的已注册 `Completed`；绝不输出单 RT。 |
| 某个普通单键 OnPress Chord 获胜，且 RT 是其 Trigger | `true` | 仅保留该 OnPress 动作原有释放行为。 |
| 没有获胜 Chord，release-fallback 的 Context/ExactModifier 检查通过 | `false` | 恰好一个新的 `Input.Weapon.RT` `Started`。 |
| 没有获胜 Chord，但 Context/ExactModifier 检查失败 | `false` | 不输出任何动作。 |

“消费”与现有 `bConsumeTriggerControls` 不是同一个概念：只要**获胜 Chord 的任一成员**是该物理键，就必须消费该键的 release-fallback；不能因为获胜 Chord 的 `bConsumeTriggerControls=false` 而在松开时泄漏单 RT。

## 5. 精确执行流程

### 5.1 物理 Started

`HandlePhysicalStarted(PhysicalTag, Now)` 保持现有顺序：分配 `SequenceID`、写入 `HeldControls`、更新 Aim 子 Tag、评估普通 Chord。

M4.3 的差异只有：

1. `EvaluateChords`、`IsPossiblyCompletable` 和延迟胜出逻辑必须跳过 `DispatchPolicy=OnReleaseIfUnconsumed` 的 Chord；它永不在按下、Grace 到期或组合完成时 `EmitChord`。
2. 若物理 Tag 属于 `ReleaseFallbackOwnedTags`，不得走“无组合单键立即发出”、`FlushExpiredInputs` 的原始单键回退或快速松开前的原始单键回退。
3. 一个普通 `OnPress` Chord 胜出时，`EmitChord` 在现有 `bSingleConsumed` 处理之外，遍历其 `Members`；任何仍在 `HeldControls` 中的成员都置 `bReleaseFallbackConsumed=true`。

`EmitChord` 仍按当前逻辑建立普通 Chord Snapshot、可选注册 `ReleaseControlTag`、再 `EmitSnapshot`。M4.3 不改变其 `SequenceID` 分配方式。

### 5.2 物理 Completed

`HandlePhysicalCompleted(PhysicalTag, Now)` 必须在移除 `HeldControls[PhysicalTag]` 前按以下顺序工作：

1. 只从普通 `OnPress` Chord 中选出当前已经完整的最佳获胜者；若有，按现有 `EmitChord` 处理，它会消费当前物理键的 release-fallback。
2. 现有“快速松开时发送普通单键 fallback”的分支必须跳过 `ReleaseFallbackOwnedTags`。
3. 若该 PhysicalTag 有 release-fallback、对应 `FPhysicalInputState` 尚未被消费，则用对应 Chord 的 **当前** `IsChordComplete` / Context / ExactModifier 结果重验。此时物理键仍处于 Held，因此检查与正式 Chord 的 Context 语义一致。
4. 检查通过时立即构造候选 Snapshot：
   - `ResolvedInputTag = Definition.OutputTag`；
   - `SourceControlTag = PhysicalTag`；
   - `SequenceID = State.SequenceID`，复用本次物理按压身份，不调用 `AllocateSequenceID()`；
   - `Phase = Started`、`Timestamp = Now`；
   - 方向、姿态、HeldModifier、Aim 均在**松开时**冻结；构造时该 PhysicalTag 尚在 HeldControls 中。
5. 按现有顺序处理 `ReleaseRegistry[PhysicalTag]`，向已存在的激活动作发送其 `Completed`。M4.3 不新增或修改这些注册。
6. 若第 4 步有候选 Snapshot，在 ReleaseRegistry 分发后调用一次 `EmitSnapshot`；**不**调用 `RegisterRelease`，也不补发 `Completed`。
7. 移除 Held 状态、重置受该键影响的普通 Chord 解析状态、重算 Aim 子 Tag，完全复用现有收尾。

因此 release-fallback 的 `Started` 是一次新的离散武器输入，发生在松开这一刻；它不是“把按下时被延迟的 Snapshot 补发”，也不是给某个已激活动作的释放通知。

### 5.3 边界生命周期

| 事件 | 要求 |
|---|---|
| `SetInputProfile` | 复用现有“保留 held、重置 formation”的合同；同时将所有保留 HeldState 的 `bReleaseFallbackConsumed=true`，禁止旧 Profile 下按下的键在新 Profile 下松开时生成新 release-fallback。新 Profile 生效后的新物理按压才可生成。 |
| `AttachToPawn` / `ShutdownRouter` / `EndPlay` | 现有 `HeldControls`、`DeferredChords`、`ReleaseRegistry` 清理同时消除 release-fallback 资格；晚到的 Completed 必须无副作用。 |
| 物理键重复 Started | 保持现有幂等拒绝；不能分配第二个 SequenceID。 |
| Context 在按住期间变化 | 只以松开时、键仍 Held 的 ContextTags/ExactModifier 状态决定是否发出；不使用按下时的姿态替代。 |
| 获胜组合在松开前已发出 | 已由 `bReleaseFallbackConsumed` 永久屏蔽本次按压；即使随后松开其他组合成员，也不得回退单 RT。 |

## 6. 实现顺序与文件级任务

### 6.1 Profile 与校验

1. 在 `MHGZWeaponInputProfile.h` 增加枚举与默认 `DispatchPolicy=OnPress` 字段。
2. 在 `IsDataValid` 的每条 Chord 校验中增加第 3.2 节规则；使用本地 `TMap<FGameplayTag, int32>` 记录 release-fallback Trigger，报错须同时包含两个 Chord Index 与 PhysicalTag。
3. 不能修改既有重复 Chord、ReleaseControlTag 或普通 `OnPress` 的合法规则。

### 6.2 Router 缓存与辅助函数

1. `RebuildChordCache` 重置并重建 `ReleaseFallbackChordByControl`、`ReleaseFallbackOwnedTags`。
2. 为可读性添加私有辅助函数，建议名称：
   - `bool IsReleaseFallbackChord(int32 ChordIndex) const;`
   - `void ConsumeReleaseFallbackForMembers(const FChordInfo& Winner);`
   - `TOptional<FWeaponInputSnapshot> BuildReleaseFallbackSnapshot(FGameplayTag PhysicalTag, const FPhysicalInputState& State, double Now) const;`
3. `BuildReleaseFallbackSnapshot` 必须验证映射、未消费状态和 `IsChordComplete`，并按第 5.2 节构造 Snapshot；它不改变状态、不注册释放。
4. 不把这些私有辅助函数暴露给 Blueprint，也不把消费账本放进 ASC 或 RuntimeHost。

### 6.3 Router 事件接入

1. 修改普通 Chord 搜索、延迟候选和 Completed 前的最佳 Chord 搜索，使其只考虑 `OnPress`。
2. 在 Started、Grace timeout、快速释放的原始单键 fallback 分支中排除 `ReleaseFallbackOwnedTags`。
3. 在普通 `EmitChord` 成功确定赢家后消费所有当前 Held 成员的 release-fallback，再保持原有 `bSingleConsumed` / `ResolvedChords` / `ReleaseRegistry` 行为。
4. 在 Completed 的 ReleaseRegistry 分发前构造 release-fallback Snapshot、之后发送它；调用路径只能到 `EmitSnapshot`。
5. `SetInputProfile` 中对仍 Held 的按键置 `bReleaseFallbackConsumed=true`，防止跨 Profile 按压泄漏。

| 测试 | 输入序列 | 必须断言 |
|---|---|---|
| `ReleaseFallbackEmitsOnce` | RT Started，RT Completed | 按下无输出；松开恰好一个 `Input.Weapon.RT/Started`；Source=物理 RT、SequenceID=该按压、Timestamp=松开时；无 `Completed`。 |
| `WinnerConsumesFallback` | RT + 任一完整普通组合，随后松开 RT | 只出现组合的既有输出/释放；绝不出现 `Input.Weapon.RT`。必须覆盖 RT 为 Modifier 的组合。 |
| `QuickReleaseDoesNotWaitForGrace` | RT Started 后在 Grace 内 Completed，未形成组合 | 松开立即输出一次 release-fallback；不依赖 `FlushExpiredInputs`。 |
| `ReleaseRechecksContextAndExactModifiers` | 按住后使 Context 或 ExactModifier 条件不满足，再松开 | 不输出 fallback；验证决策不是按下时冻结。 |

| `ProfileSwapAndShutdownDoNotLeak` | RT 按下后 Profile swap 或 Shutdown，再 Completed | 不得产生 release-fallback；晚到回调无副作用。 |
| `ValidationRejectsIllegalPolicies` | 多 Trigger、有 Modifier、有 ReleaseControlTag、同一 Trigger 两条策略 | `UWeaponInputProfile::IsDataValid` 均返回 Invalid，并报告相应 Chord/Tag。 |

完整回归至少运行：

前者验证新策略，后者证明 Chord 排序、冻结快照、ReleaseRegistry、快速释放、Profile/Ownership 重绑没有回归。

## 9. 禁止的替代实现

- 不在 `HandlePhysicalStarted` 启动计时器、延迟后补发单 RT；这会让持有时长而非“是否被消费”决定行为。
- 不在 `UMHGZAbilitySystemComponent` 或 ComboCoordinator 猜测 RT 是否与 A/B/Y/LT 组合；消费事实只属于 Router 的物理按压状态。
- 不复用 `ReleaseRegistry` 发送“RT 的 Completed 后再 Started”；新动作的 `Started` 必须由 Router 直接输出，且没有同键补发 Completed。
- 不通过修改 `ChordGracePeriod`、Priority、`bConsumeTriggerControls` 或 InputProfile 重排来模拟 release-fallback。
- 不提前把动作退出、虫印斩伤害或 GA 绑定加入本阶段。
