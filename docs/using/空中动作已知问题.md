## 1. 无白灯后撑杆跳（**既有**，非回归）

### 1a. 下坠交接处一帧卡顿（**用户主诉**，2026-09-18 更正定位）

**用户原话**：「顿一下指的是**下坠**的时候，而不是上升的时候，大概是 JumpOver 切 Fall 的时候」。

**实测坐实**：CurvedVault 源的**末帧之后那一帧**，下坠量从约 −28 cm 掉到约 −9 cm，再恢复：

| | 20260918-205813（已修） | 20260917-210929（重构前） |
|---|---|---|
| 源末帧 `dZ` | −27.91 | −27.77 |
| **交接帧 `dZ`** | **−9.73** | **−8.61** |
| 次帧 `dZ` | −29.43 | −28.39 |
| 交接帧 `dVZ` | **0.0** | **0.0** |

**两版逐帧一致 ⇒ 既有。** `Velocity.Z` 全程连续（−1114.7），所以不是速度跳变，是**那一帧的位移被截断**，一帧约丢 17~19 cm —— 所以「不明显」。

**已排除**：碰撞（整段飞行只有落地那一次胶囊命中，法线 Z=1）；采样假象（那段 0.1 s 内 Z 实降 −100.9 cm，而 `VZ` 积分预测 −118.2 cm，缺 17 cm 是真实的）。

**机制（已定位到引擎行）**。`FinishVelocityParams` 的安装点是 `FRootMotionSourceGroup::CleanUpInvalidRootMotion`（`RootMotionSource.cpp:1346`，装速度在 `:1381-1401`），由 `UCharacterMovementComponent::PerformMovement` 在开头调用（`CharacterMovementComponent.cpp:2743-2753`）。**帧内顺序是 `CleanUp → PrepareRootMotion → StartNewPhysics`。** 于是卡顿那一帧：

1. 帧开始时源**还没**被判完成（遥测末帧 `cT=1.075 < Duration=1.083`），`CleanUp` 不动它 ⇒ 切线速度**没装上**；
2. 紧接着 `PrepareRootMotion` 把时间推过 `Duration`、标 `Finished`，而它只产出路径**剩下的那 0.4%**（进度 0.8767 → 0.8808）⇒ 这一帧的位移就是这点残量；
3. 到**下一帧**的 `CleanUp` 才移除源并装上 `SetVelocity` 切线 ⇒ 从下一帧起恢复 −29.43。

**一句话：源过期的那个部分帧只走了路径残量，而切线速度要等下一帧才装得上，中间正好丢一帧。**

**注意 `ApplyCurvedVaultSource` 已经做对了**（切线在建源时就装进 `FinishVelocityParams`，注释写着「removes the frame-order dependency entirely」）—— 那句话在**值**上成立，在**帧**上不成立。

**修法建议（未实施，建议与 A6 同批）**：用户已指出**地面攻击动作结束也有同款问题** ⇒ 这是**所有** movement task 收尾的通用帧量化效应，不是 CurvedVault 独有。应当做一次通用修复（例如让源不在帧中途过期：把 `Duration` 收到帧边界内，或由 `TickTask` 在跨过 `Duration` 的前一帧主动收尾），而不是为 CurvedVault 单独打补丁。

**顺带**：这段下坠 cT 0.725→1.076 在两版之间**逐帧数值相同**，而旧版 `MovementMode` 到末帧才由 5 变 3、新版早在 0.80 就变 3 ⇒ **换模式对下坠轨迹没有任何影响**，两个积分器的差异在这条弧上测不出来。

### 1b. 上升段起跳后约 0.33 s 完全不动（**不是用户说的那处**，但确实存在）

**现象**：`AM_IG_HouChengGanTiao` 起跳后，胶囊在 `Z=98.2` 原地停 13 帧（约 0.325 s），`Velocity.Z` 恒为 0，然后才被蒙太奇根运动推起来；随后在 `Z=196.7` 处有**一帧** `VZ 452.7 → 0` 的塌陷，再交给 CurvedVault 源。

**证据（三份实录逐帧数值完全一致）**：

| 实录 | 13 帧静止 | 塌陷帧 `VZ` | 之后 |
|---|---|---|---|
| `20260917-210929` | 有 | `452.7 → 0.3` | `235.5 / 1555.3` |
| `20260917-021641` | 有 | `455.2 → 1140.0` | `225.1 / 1140.0` |
| `20260918-141711` | 有 | `452.7 → 0.0` | `235.3 / 1555.3` |

⇒ 与本轮（点通知 + Flying/Falling 改造）**无关**，是既有行为。注意第 2、3 行的塌陷后数值本身就不一样，说明这段本来就不稳定。

**嫌疑点**：

- `BeginBackVaultInitialFlight`（`Source/MHGZ/ActionSystem/MHGZBackVaultAbility.cpp:432-450`）在蒙太奇根运动还没有产出位移之前就把胶囊放进 `MOVE_Flying`，而 `MOVE_Flying` 不跑重力 —— 没有东西驱动时就真的一动不动。
- `UAbilityTask_WaitDelay::WaitDelay(this, JumpDuration)`（同文件 `:567`）是**墙钟计时器**（`BackJumpDuration = 0.650f`），与蒙太奇真实的 Jump 段边界**没有任何断言关系**。头文件 `.h:225` 的注释写的是「Runs at the JumpOver section boundary」，与实际实现对不上。

**修的时候注意**：`Mode == BallisticVault` 的 `[VaultDbg] tick` 守卫（`AbilityTask_MHGZWeaponMovement.cpp:184`）**不覆盖 CurvedVault**，所以这段只能靠 `Saved/RuntimeTelemetry/*/Character/Spatial.csv` 的 `MovementMode` 列看。

## 2. 突进回旋斩反击：触发延迟高 + 「先播受击再起飞」（**既有**）

**现象**：按下反击后到真正起舞有明显延迟；有时先看到受击动画，然后才起飞。

**反击链本身没有延迟源**。已逐行核实：从 `HandleIncomingHit`（`MHGZAdvancingCounterAbility.cpp:218-248`）到 `ApplyBallisticVaultSource` 是**同一帧内的同步调用**，中间没有计时器、没有蒙太奇段边界、没有 suspend/resume 交接。唯一的门是 `AM_IG_TuJinHuiXuan` 里 `IG_AdvancingCounter` 那条 notify 窗口在蒙太奇时间轴上的位置。

**延迟来自训练桩**：`MHGZTrainingDummy` 的火环按 `HitInterval = 0.25 s` 提交命中（`Source/MHGZ/Monster/MHGZDummyConfig.h:121`），环本身 `ActiveDuration = 1.0`、`EmissionInterval = 5.0`（`:113`/`:117`）。所以反击只有在某次环击**恰好落进 notify 窗口**时才能触发 —— 最多等 0.25 s；窗口整个错过则要等下一个环（最多 5 s）。

**「先受击再起飞」是同一个采样的两面**：落在窗口外的环击不被消耗 → 走伤害路径 → `Combat.Event.HitStagger` → `UMHGZHitReactionAbility` → `CancelActivePlayerActions()`；下一次落在窗口内的环击被 Consume → 起身。日志 `Saved/Logs/MHGZ.log` 里能直接看到这个交替。

> **这条要改得动火环节奏（测试桩）或补空中受击表现，属于测试夹具问题，不是战斗逻辑问题。**

## 4. 勘误：`MOVE_Flying` 是 5，不是 4

上一轮的 PIE 判据里写「`mode=4`（Flying）」是**错的**。`EMovementMode` 实际顺序：

| 值 | 枚举 |
|---|---|
| 1 | `MOVE_Walking` |
| 2 | `MOVE_NavWalking` |
| 3 | **`MOVE_Falling`** |
| 4 | `MOVE_Swimming` |
| 5 | **`MOVE_Flying`** |
| 6 | `MOVE_Custom` |

本轮就是靠 `mode=5` / `mode=3` 才对上号的。后续所有判据一律用 5/3。

## 5. 舞踏起跳冻结（2026-09-18 已改，**待 PIE 验证**）

留档，避免下次误判。**症状**：舞踏起跳后冻结整整一个混入时长（`AM_IG_WuTa` 的 `BlendIn = 0.15 s`），`srcForceZ` 全程正确却进不了 `Velocity`，顶点不再是 564（实测在 640.9 / 592.6 / 401.5 / 346.5 / 54.6 之间乱跳），源只活 0.2 s。

**根因**：出招蒙太奇 `AM_IG_TuJinHuiXuan` 被挂起后按自己的 `BlendOut` 淡出，而 `UAnimInstance::Montage_PlayInternal`（`AnimInstance.cpp:2412-2426`）**只在「新蒙太奇自己带根运动」时**才去 Stop 上一个根运动实例 —— `AM_IG_WuTa` 是纯表现蒙太奇、没有根运动，那条分支根本不进。于是旧的在整个淡出窗口里一直留在 `RootMotionMontageInstance` 上、持续提取根运动，点亮 `CMC->RootMotionParams.bHasRootMotion`，使 `ApplyRootMotionToVelocity`（`CharacterMovementComponent.cpp:4410`）走动画分支并提前 `return`，把新加的 `RootMotionSource` 整段盖掉。

**修法**：`MHGZAttackAbility::SuspendAttackMontageForFollowup` 里对**正在淡出的** `ActiveAttackMontage` 实例 `PushDisableRootMotion()`，命中 `AnimInstance.cpp:1952` 的 `!MontageInstance->IsRootMotionDisabled()`。只停提取，不动混合。

**顺带两条教训**：

1. `CMC->HasAnimRootMotion()` 读的是 `CMC->RootMotionParams.bHasRootMotion`（`CharacterMovementComponent.h:2771-2776`），引擎注释明写 **"Not valid outside of the scope of that function"** —— 从能力任务 tick 里读它**永远是 0**，不构成任何证据。曾因此差点放过真凶。
2. 同一帧里 `IsPlayingRootMotion()`（`SkeletalMeshComponent.cpp:4529-4544`）= 1 与 `HasAnimRootMotion()` = 0 并不矛盾，它们读的不是同一个东西。
